Security & Architecture

Data flows, trust boundaries, offline capability, and limitations for organizational security reviews.

Last updated: October 26, 2026

Architecture overview, not an audit: this is a logical diagram of the current open-source implementation, not a guarantee about every network packet, a penetration-test report, a security certification, or approval to process CJI.

1. Logical network and data-flow diagram

Trust boundaries

User-controlled device: original PDF files, camera photos, extracted text, signing keys, random page salts, and the sealed output are handled in the browser by the current document workflow. Device security and any downloads or onward sharing are the user's responsibility.

QRed's Cloudflare deployment: serves application resources and exposes a small Worker API for public configuration, key information, sign-in, and account-backed attestations. Its authority signing seed is a configured Worker secret and is not returned to browsers.

External identity providers: Google, Microsoft, Facebook (Meta), and Amazon handle sign-in under their own systems. These providers do not receive the original document or its page commitments from QRed's sign-in requests.

Recipients: obtain printed or digital sealed documents through whatever channels the sender chooses. They may verify signed payloads using QRed's bundled authority trust anchors or independently obtained local signer public keys.

QRed's current implementation does not maintain a database of user accounts or uploaded documents. Account authentication uses secure encrypted, document-bound cookies that expire after approximately ten minutes. Network/hosting telemetry and identity-provider records can exist separately.

3. Provider-specific authentication

All four providers are optional and independently configured. Their availability can change by deployment; an unconfigured provider should not be described as enabled.

  • Google: server-side OAuth code exchange; verified Gmail or eligible Workspace identity.
  • Microsoft: single-page application authorization code with PKCE, redeemed in the browser; QRed Worker validates the signed ID token. No Microsoft client secret.
  • Facebook (Meta): standard server-side OAuth code exchange. The Worker verifies the resulting access token using Meta's debug_token endpoint, checks that the token is valid and bound to QRed's App ID and user, and fetches a matching name/email profile. A signed OIDC identity token is not required. Live provider approval and real-account verification remain necessary.
  • Amazon: server-side authorization code exchange, token validation, and authenticated account profile lookup.

The Worker binds identity and the ordered page commitments to a short-lived session. QRed does not independently verify legal identity or organizational signing authority from profile names. For Microsoft, Meta and Amazon, a provider-reported email must not be interpreted as QRed independently verifying ownership of that mailbox.

4. Limits of authentication and document evidence

Signatures authenticate the bytes actually covered by their signed QRed payload, not necessarily every aspect of the visible printed or scanned document. QR recovery, OCR, image quantization, camera quality, layout changes, and later physical alterations can affect detection. Original pages may include graphics, form marks, or fine details that lossy visual evidence does not fully preserve.

Recipients should compare recovered signed text and visual evidence with the document and verify the trustworthiness of the relevant public key. Public account trust anchors are bundled with the application; an offline copy cannot learn that a trust anchor was revoked until updated. A local public key received from an untrusted party is not proof of issuer identity.

Confidentiality warning: QRed QR payloads can reveal document text and attested profile details to compatible readers. A cryptographic seal does not encrypt a document or prevent distribution.

5. Security evidence and organization reviews

Implementation and automated tests are available in QRed's repository; CI runs provide repeatable evidence for tested functionality. Tests do not replace independent penetration testing, operational monitoring, organization-specific risk assessment, incident-response plans, or compliance authorization.

For an organization handling criminal justice information, QRed does not claim CJIS compliance or authorization. An organization's responsible officials should review endpoint security, hosting and subcontractor obligations, network egress, identity assurance, key management, auditability, retention, accessibility, and printed/sealed-document disclosure risk. An offline-capable browser application is not automatically suitable for processing CJI.
